Section 1

Structure is the first version control

Branching only pays off when there's a clear "main" worth protecting. Before any branch is cut, the space itself has to say what's canonical. On the Organization plan we get unlimited teams and projects, so we can structure by how we actually work: one team per platform surface — PBS.org on the web, and the PBS App split into its two surfaces, Mobile and CTV — plus one team for the shared systems everything consumes.

File naming

Files are named so search works and duplicates are obvious: surface, then feature, then the ticket when one exists.

PatternExample
Surface · Feature — TicketApp CTV · Video Player — DES-214
Library files: plain names, no datesApps Design System, Brand Assets
Neverplayer-final-v3-FINAL (2) — versions live in version history now, not filenames

The standard page template

Every product file uses the same page skeleton, so "where is the shipped comp?" has one answer in every file. Duplicate the team template file to start new work.

Pages
  • 📕 Cover — owner · status · links
  • — ready —
  • ✅ Ready for dev
  • — working —
  • 🚧 In progress
  • 🧪 Explorations
  • — context —
  • 🔀 Flows & research
  • 🧱 Local components
  • 🗄 Graveyard

Work moves up the file as it matures: Explorations → In progress → Ready for dev. Nothing is deleted mid-project — rejected directions go to the Graveyard page so decisions stay traceable.

Section 2

Named versions: our save points

Figma autosaves a checkpoint roughly every 30 minutes, but autosaves are anonymous — nobody can find "the version we showed the stakeholders" in a wall of timestamps. A named version (⌘⌥S / Ctrl+Alt+S) is a deliberate save point with a title and description, and on paid plans history is retained indefinitely.

When we name a version

  • Before starting a big change or restructure — the "last known good."
  • After every milestone review — stakeholder share-outs, design crits, accessibility passes.
  • At handoff — the moment something is marked ready for dev.
  • At merge — Figma records branch merges automatically, but add a named version when a merge changes what "shipped" means.

Naming convention

FieldConventionExample
Title (25 chars max)v0.x exploring · v1+ shipped, then milestonev1.2 — Stakeholder rev
Description (~140 chars)What changed + what's still open"Player rail approved; captions menu still pending a11y review."

Restore is non-destructive

Restoring an old version doesn't erase anything — the current state stays in history, and comments from all versions are kept. You can also duplicate any version out as its own file, which is how we snapshot a comp for an external partner without freezing the working file.

Section 3

Branching: the Org-plan unlock

A branch is a controlled copy of a file where you can explore, restructure, and even edit library components without touching the original. The main file stays the single source of truth the whole time; when the work is approved, it merges back with a reviewable diff. This is the feature the upgrade was for — and it's most valuable on the files the whole org consumes.

When to branch — and when not to

Branch rules

RuleDetail
Name = ticket + intentDES-812 — Player rail. No ticket? Use your initials: MC — Nav explorations.
One initiative per branchSmall, focused branches merge cleanly. Don't batch unrelated changes.
Pull from main oftenAccept main-file updates at least weekly. Updates apply all-or-nothing, so drift is the enemy.
Reviews required on librariesMerges into Apps Design System and Brand Assets require an approval from the library owner. Product-file branches need one peer review.
Merge, then publishLibraries can only publish from the main file — merge first, publish second, and add a named version describing the release.
Prune stale branchesAnything untouched for 30 days gets merged or archived at design ops review.

Cross-file work: when a branch needs the design system

Branches are scoped to one file, full stop. You can branch the design system too, but a product-file branch and a design-system branch are two separate, unaware branches — no file can consume components from a library branch, because branch assets only exist inside that branch until it merges, and libraries only publish from main.

Local-first, promote later is how we handle it: while working in your product-file branch, draft the new or modified component as a local component right there — that's exactly what the Local components page in our template is for. You keep full momentum, and the exploration lives safely in your branch. Once the direction is approved, promote it: cut a design-system branch, move the component in (matching DS conventions), review → merge → publish, then swap your local stand-in for the real library instance before your product branch merges. Tag both branches with the same ticket (DES-812 — Player rail in both files) so the pair is discoverable.

The mental model: the product branch answers "is this the right design?" and the DS branch answers "is this the right system change?" — Figma forces you to answer them in that order, which is annoying mid-flow but is also why the library never contains half-approved parts.

Know the edges

  • Comments on the main file don't appear in branches, and branch comments don't merge back — decisions worth keeping go in the branch description or an annotation.
  • You can't publish a library from a branch — consumers only ever see merged, reviewed changes. That's a feature, not a bug.
  • Branching requires a Full seat — but not edit access: a Full-seat teammate with view-only access to a file can still create a branch, and merging then goes through a review by someone with edit access.

Section 4

Annotations, statuses & handoff

Comments are conversations; they scroll away and resolve. Annotations are specs: pinned to a layer, they can reference live properties (spacing, sizing, alignment) that stay accurate as the design changes. With engineering partners in Dev Mode, annotations are how our intent survives the handoff.

Which tool, when

SituationUseWhy
"Should this be blue?"CommentIt's a discussion — it should resolve and disappear.
"This animates in over 300 ms"Annotation (Interaction)Spec that must survive until built.
"Focus order goes rail → menu"Annotation (Accessibility)A11y intent lives with the design, not in a doc.
"This is what we showed leadership"Named versionA save point people need to find later.
"I want to try a different rail layout"BranchExploration that shouldn't touch main.

Our annotation categories

Figma ships four editable categories; we keep them and assign owners. Development (build notes), Interaction (motion, states, remote-control behavior on CTV), Accessibility (focus order, captions, contrast — every Ready-for-dev frame gets at least one pass), and Content (voice, terminology, UX copy rationale).

Statuses close the loop

  • Mark finished frames/sections Ready for dev — they surface in a dedicated Dev Mode list and engineers get notified.
  • Engineers (or we, at sprint close) mark built work Completed — an Org-plan status that turns the file into a live record of what shipped.
  • Engineers use Compare changes in Dev Mode to diff a frame against the version they last built from — one more reason named versions at handoff matter.

Section 6

The first 30 days

Don't roll everything out at once — sequence it so each habit has a week to stick.

Week 1

Structure

Stand up teams + the four projects, move files, add cover pages. Agree on the page template.

Week 2

Named versions

Start the v-numbering habit on active files. Backfill a named version on anything currently in review.

Week 3

Branching pilot

Pilot on one Apps Design System change: branch, review, merge, publish. Debrief as a team.

Week 4

Annotations + dev

Bring engineering in: annotation categories, Ready-for-dev flags, Completed status. Then make it all policy.

After 30 days: the monthly hygiene review keeps branches pruned, archives current, and the template honest.

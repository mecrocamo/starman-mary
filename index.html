1
Team Setup
Run once per project — creates the scaffolding everything else depends on
Cowork Code
›
✦ New in this phase: design-audit — gives designers the same project orientation that analyze-codebase gives engineers.
teamcraft-setup
Verifies Jira, Confluence, and GitHub connections. Nothing else functions without this.
The prerequisite for all other TeamCraft skills. Checks that your MCP connections to Atlassian and GitHub are authenticated and working. If any connection is broken, it guides you through fixing it before you waste time on downstream skills.
init-project
Creates CLAUDE.md, project.md, .claude/rules/, and CI workflows — the local project context every developer session loads automatically.
Sets up the project scaffold that every developer session loads automatically. Without it, plan-and-implement-issue starts cold with no project awareness. Includes GitHub Actions CI config with test, lint, and security jobs.
analyze-codebase
Maps an existing codebase — architecture docs, ADR candidates, component rules, and convention gaps.
Essential for brownfield projects. Runs a quick-pass analysis (tech stack, structure, patterns), then offers deeper output: architecture documentation, component-level rules, ADR candidates, and a comparison against team conventions.
New
design-audit
Inventories the existing UI — component patterns, design system coverage, visual inconsistencies, and accessibility gaps — before the project begins.
The design counterpart to analyze-codebase. Connects to Figma to map what components and patterns already exist, flags where the live UI diverges from the design system, and surfaces accessibility or consistency issues that should be resolved before new work layers on top. Produces a design health summary in Confluence that feeds into capture-requirements and define-roadmap.
learn-teamcraft
Teaches the workflow — full overview or role-specific deep dive. No environment access needed.
Run it any time you want to understand the plugin better, onboard a new team member, or refresh on how the phases connect. Advisory only — never starts work.
onboard
Orients a new team member by reading Jira, GitHub, and Confluence project artifacts, then explaining the current state.
Run when joining an existing project mid-sprint. Reads live project data and explains what's in progress, what's been decided, and how the team works. Advisory only — never starts work or modifies anything.
2
Product Definition & Planning
Where everything the team builds originates — upstream collaboration before a single line of code is written
Cowork
›
The upstream anchor phase. The PRD, roadmap, tech decisions, and sprint issues produced here are auto-loaded into every developer planning session. Quality here = less ambiguity downstream.
✦ New in this phase: design-handoff closes the gap between design completion and developer pickup — replacing informal Figma links with a structured, loadable spec.
discover-problem
Facilitate structured discovery with a client or stakeholder before requirements are written. Produces a Confluence summary seeding capture-requirements.
Run during a meeting or call. Guides structured exploration of a problem space to produce a sharp problem statement. Surfacing user needs, mental models, and edge cases here shapes what gets built. Output lands in Confluence and feeds directly into capture-requirements.
capture-requirements
Run a live requirements session, generate visual mockups to confirm understanding, and produce a structured PRD in Confluence.
The primary requirements tool. Generates interactive visual mockups during the session so clients can validate understanding before it becomes a spec. Mockups and interaction intent captured in the PRD reduce rework during implementation.
define-roadmap
The planning layer between the PRD and sprint work — sequences what gets built across sprints, with priorities and dependencies.
Sits between a baselined PRD and sprint planning. Answers: what gets built in what order, across how many sprints, and why? Flags which sprints need design-heavy lead time and where dependencies might affect sequencing. Stored in Confluence, feeds directly into plan-sprint.
plan-sprint
Turns the PRD into Jira backlog issues with acceptance criteria, creates the sprint, and adds issues to it.
Creates well-formed Jira issues with acceptance criteria, technical guidance, and testing requirements from the PRD. Creates the sprint and adds the issues to it. The quality of issues here directly determines the quality of what developers build.
create-issue
Create a single Jira issue at any time — ad-hoc bugs, mid-sprint requests, client feedback, or design findings.
For work that arrives outside sprint planning. Same quality standards as plan-sprint issues. Useful for filing issues when design reviews surface problems, inconsistencies, or missing interactions that need to be tracked and fixed.
tech-decisions
Records the technology stack and key architectural choices in Confluence — auto-loaded into every developer planning session.
These decisions are invisibly loaded into every plan-and-implement-issue session. Without it, each developer independently chooses libraries and patterns — and those choices diverge over time.
capture-conventions
Documents coding standards, review process, and branching rules in Confluence — flows into developer sessions automatically.
Provides the scaffolding that makes the build loop produce consistent, review-ready code. The conventions captured here affect how design specs get implemented in practice.
New
design-handoff
Packages Figma frames, interaction notes, component specs, and open design decisions into a structured document loaded automatically by plan-and-implement-issue.
Currently, design intent reaches developers as an informal Figma link in a Jira ticket — if that. This skill formalizes the handoff: pulling the relevant Figma frames for the sprint's issues, annotating interaction intent, flagging open decisions that need developer input, and producing a structured handoff document in Confluence. plan-and-implement-issue loads this alongside the PRD so developers plan against real design specs, not assumptions. Requires Figma connection.
3
Build Loop
Repeated for every issue — the developer's daily rhythm in Claude Code
Code only
›
How upstream work reaches developers: plan-and-implement-issue auto-loads the PRD, tech decisions, and team conventions. With design-handoff in place, Figma specs and interaction notes load here too — no separate handoff needed.
fetch-issue
Loads the Jira issue and scans the codebase for relevant existing code before any planning begins.
The starting point for every piece of work. Answers: is this issue ready to build, partially started, already implemented, or blocked? Produces a feasibility assessment. Read-only — no changes made here.
plan-and-implement-issue
Loads all project context, enters plan mode, creates the feature branch, opens a Draft PR, and implements with TDD discipline unit by unit.
The core build skill. Loads tech decisions, conventions, PRD context, and live library docs — then plans and implements the solution. With design-handoff in place, Figma specs and interaction intent load here automatically. Developer reviews after each unit before proceeding.
complete-issue
Runs code health, security, and deviation reviews automatically. Pushes the branch and marks the PR ready for human review.
The automated quality gate before any human sees the PR. Runs three checks: code health, security scan, and deviation review. Then pushes and marks the Draft PR ready.
fast-path
Urgent work that can't wait for sprint planning — skips ceremony but preserves all quality gates.
For production bugs, critical fixes, and emergency work. Streamlines the path from issue to PR without sprint planning ceremony. All quality gates still apply — fast-path removes ceremony, not safety.
4
Review & Merge
PR feedback loop through to merge and Jira closure
Code only
›
✦ New in this phase: design-review — the highest-impact addition. Adds a design gate alongside the existing code review so visual drift is caught before merge, not after.
pr-review
Reviewer's tool — reads the full PR diff and comment threads, leaves feedback, approves or merges without leaving Claude Code.
Loads the full PR diff, implementation context, and open discussion threads. Reviewer can leave structured comments, respond to threads, request changes, approve, or merge — all from the CLI without switching to the GitHub UI.
New
design-review
Pulls the relevant Figma frames for the PR and compares them against the implementation — flags drift, missing states, and interaction gaps before merge.
The most critical missing step in the current workflow. Runs alongside pr-review and answers: does what was built match what was designed? Connects to Figma to pull the spec frames for the relevant issue, takes a screenshot of the implementation, and produces a structured comparison — flagging visual drift, missing interaction states, accessibility issues, and spacing/typography deviations. Leaves review comments on the PR just like pr-review. Requires Figma connection.
address-feedback
Author's tool — polls for open reviewer threads, makes code changes, and pushes updates.
Surfaces all open PR threads — including design-review threads — and helps the author decide what to change vs. reply to. Makes the changes and pushes. Leaves the PR ready for the reviewer's next pass.
post-merge
After merge: explicitly closes the Jira issue, cleans up stale status, and syncs local git state.
⚠️ Important: GitHub PRs do NOT auto-close Jira issues. Without this step, tickets stay open even after code ships. post-merge explicitly transitions the Jira issue to Done and syncs local git.
5
Visibility
Available to anyone at any time — no codebase access needed
Cowork
›
✦ New in this phase: design-qa — makes design findings as trackable as engineering bugs, captured as properly formed Jira issues rather than Slack threads.
project-health
On-demand sprint health — progress, velocity, quality signals, defect trends. Returns insight, not raw data.
Pull a health snapshot at any time. Synthesizes Jira sprint data and GitHub signals into an interpreted summary with flags and recommendations, not just numbers.
stakeholder-update
Generate audience-appropriate status reports from live Jira + GitHub data — client update, exec summary, engineering digest.
Pulls live sprint and PR data and shapes it for its audience. A client update emphasizes what shipped and what's next. An exec summary focuses on risk and timeline. Stored in Confluence.
pipeline-health
When CI breaks or stalls, explains what failed and why in plain language. Can create a Jira issue from persistent failures.
Interprets GitHub Actions workflow failures in plain language. Returns: what failed, why, and suggested next steps — not raw logs.
qa-support
Surfaces what's ready to test in the current sprint. Prepares test approaches and captures bugs as properly formed Jira issues.
Works without codebase access. Use to understand what's ready for testing, prepare a structured test approach for a specific issue, or capture a bug as a properly formed Jira issue with reproduction steps and severity.
New
design-qa
Captures design findings from review sessions as properly formed Jira issues — visual bugs, missing states, accessibility issues, and interaction gaps.
The design counterpart to qa-support. When a designer reviews shipped features and finds issues — a truncated label, a missing hover state, a color that doesn't meet contrast ratios — this skill turns those findings into properly formed Jira issues rather than Slack threads or sticky notes. Each issue includes the relevant Figma frame, a description of the expected vs. actual state, severity, and suggested fix. Works without codebase access.
6
Continuous Improvement
Retrospectives and living documentation — keeps the system healthy over time
Cowork
›
sprint-retro
Structured sprint retrospective from Jira data — facilitates the conversation and writes the report to Confluence.
Gathers sprint data via an analysis agent, then facilitates the retrospective conversation — what went well, what didn't, what to try next. Captures team insights and writes a structured report to Confluence. A whole-team activity.
sync-project-docs
Keeps CLAUDE.md and project rules current as the project evolves — adds new patterns, removes stale ones.
Run mid-ticket, end of sprint, or whenever the codebase drifts from what CLAUDE.md describes. Audits current docs against the live codebase and proposes updates.
